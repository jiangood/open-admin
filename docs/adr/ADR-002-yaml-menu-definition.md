# ADR-002: YAML 菜单定义

## 状态

✅ 已采纳（2024-Q1）

## 上下文

open-admin 需要管理前端菜单树和后端权限码。传统做法是将菜单和权限存储在数据库表中，通过管理界面维护。但我们发现这种方式存在以下问题：

1. **开发效率低**：每新增一个页面，需要先登录管理后台添加菜单和权限，再编写代码。
2. **环境同步困难**：开发、测试、生产环境的菜单配置难以保持一致，数据库迁移脚本繁琐。
3. **权限码分散**：权限码散落在数据库和代码中，难以统一审查和维护。
4. **多项目复用**：框架需要提供默认菜单，业务项目在此基础上扩展，数据库方式难以实现分层合并。

## 决策

采用 **YAML 文件** 定义菜单结构和权限配置，通过 `menu-lib.yml` 和 `dict-lib.yml` 分别管理。

### 实现细节

- 菜单定义放在 `config/menu-lib*.yml` 文件中，字典定义放在 `config/dict-lib*.yml` 文件中，均支持多文件通配合并。
- 框架提供默认菜单（系统管理），业务项目通过同名 ID 覆盖或扩展。
- 使用 `DataPropertiesFactory` 在应用启动时解析 YAML，合并多文件配置，缓存为 JSON。
- 通过 `SysMenuRepositoryYamlImpl` 提供菜单查询接口，与数据库查询接口互换。

### 关键代码

```yaml
# config/menu-lib.yml
data:
  menus:
    - id: sys
      name: 系统管理
      seq: 10000
      icon: SettingOutlined
      children:
        - id: sys-user
          name: 用户管理
          path: /system/user
          icon: UserOutlined
          perms:
            - {name: 读取, code: read}
            - {name: 创建, code: create}
            - {name: 更新, code: update}
            - {name: 删除, code: delete}
```

## 理由

1. **声明式配置**：菜单结构一目了然，与代码一起版本控制，无需额外维护数据库脚本。
2. **开发流程简化**：新增页面时，只需在 YAML 中添加菜单定义，随代码一起提交即可。
3. **多文件合并**：框架提供默认菜单，业务项目通过 `menu-lib-{profile}.yml` 按需覆盖，同名 ID 自动合并。
4. **权限码集中管理**：权限码与菜单定义在一起，便于审查和维护。
5. **运行时不可变**：菜单结构在启动时确定，运行时不会意外修改，减少运维复杂度。

## 后果

### 正面

- 菜单配置与代码同源，环境一致性有保障。
- 新增页面流程简化：写代码 → 配 YAML → 提交。
- 框架与业务项目的菜单可分层定义、自动合并。
- 支持通配符多文件加载，便于多模块拆分。

### 负面

- 菜单变更需要重启应用，不支持运行时动态调整。
- 不适合需要频繁动态修改菜单的业务场景（如 SaaS 多租户自定义菜单）。
- YAML 文件随菜单增多可能变得庞大，需要合理组织。

## 替代方案

- **数据库存储菜单**：适用于需要运行时动态调整菜单的场景。可通过实现 `SysMenuRepository` 接口切换为数据库存储。
- **数据库 + 缓存**：兼顾动态性和性能，但增加了系统复杂度。
